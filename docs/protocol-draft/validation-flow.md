# 验证流草案 / Validation Flow (draft)

**Status: `Draft`（非规范性）**。定义校验的**顺序、短路与不变量**，不定义代码。

对应 `docs/handover/api-sketch.md` 的断言 A1–A7、B1–B6。此文件解释"为什么按这个顺序"。

---

## 1. 顺序原则

**先廉价，后昂贵；先本地，后上下文。**

```
解析（结构/长度/字段合法性）        ← 最廉价，拒掉绝大多数垃圾
  ↓
签名校验                            ← 中等
  ↓
输入存在性与双花检查（状态查询）     ← 较贵
  ↓
条件/脚本执行（受静态资源上界约束）  ← 最贵
  ↓
遮蔽证明校验（如启用）               ← 最贵，且依赖密码学选型
```

任何阶段失败即**短路返回**，不继续后续计算。原因码必须唯一（见 api-sketch §6）。

## 2. 区块验证顺序

```
父块存在且哈希匹配
  ↓
版本位与扩展标志位均在已定义集合内
  ↓
时间戳容差 + 中位时间规则
  ↓
默克尔根复算
  ↓
PoW 满足难度目标
  ↓
逐笔交易验证（失败则整块无效，并指明 tx id）
```

PoW 放在交易校验之前，理由：伪造区块概率极高，先用一次哈希计算筛掉，避免为垃圾块做全量交易校验。

## 3. 不变量（任何实现不得违反）

1. **无跳过路径**：不存在"快速模式""信任模式""调试模式"可以绕过任一阶段（VF-03）。
2. **未定义即无效**：未知字段、未知标志位、未知条件类型一律无效，不得忽略（BH-06、TX-09/10）。
3. **失败惰性**：条件未满足时输出保持锁定，不降级为可花费（SC-06）。
4. **确定性**：相同输入必须给出相同结果与相同原因码；禁止使用本地时钟、随机源、外部网络作为校验输入。
5. **无特权分支**：不存在按地址、公钥、实体标识给予特殊待遇的代码路径（CN-06）。
6. **离线可验**：区块与交易的**结构有效性**必须能仅凭账本数据验证，不依赖外部服务。

## 4. 错误处理

- 用户可见错误必须包含：原因码 + 涉及字段 + 建议动作（如"等待时间锁到期"）。
- 不得向对端泄露超出必要的内部状态（例如不要把完整 UTXO 集合内容回显给请求方）。
- 重复失败的对端应被降权或断开，但**不得**因此改变共识判断。

## 5. 性能与安全的取舍

- 交易并行校验（UTXO 模型下可行）会提高吞吐，但需保证双花检测仍是全局一致的。
- 批量验签可提速，但会降低"逐笔定位失败原因"的能力；建议：默认逐笔，批量仅在明确标记的非关键路径使用。
- 任何优化都不得改变 §3 的不变量；改变即需 RFC。
