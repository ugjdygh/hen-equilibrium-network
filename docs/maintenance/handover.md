# 维护者交接 / Maintainer Handover

**用途**：让"接手维护"这件事有具体动作，而不是一句"欢迎贡献"。

---

## 1. 维护权怎么形成

| 阶段 | 权限 | 说明 |
|---|---|---|
| 初期 | 创建者保留基础合并权 | 但不包揽所有评审（`GOVERNANCE.md` §3） |
| 过渡期 | 稳定活跃贡献者可申请维护权限 | 需两名现有维护者同意，记录在 `docs/review/decisions.md` |
| 维护组成形 | 由长期活跃贡献者自然确认 | 不是预设权威，不设付费席位 |
| 无人维护 | 标记 `Unmaintained` 或归档 | 不自动推进，也不授权任何人以名义募资/发行 |

## 2. 交接时必须交出的东西

- [ ] `docs/review/decisions.md` 全部决策仍然可读（含被推翻的）
- [ ] `CHANGELOG.md` 无断档
- [ ] `docs/handover/module-map.md` 的模块状态与事实一致
- [ ] 未完成事项列成清单，写明"卡在哪"
- [ ] 已知风险清单（白皮书 §11）未被悄悄删减
- [ ] 对外口径（README 五条）未被改写为营销语
- [ ] 仓库描述、Topics、About 栏与实际阶段一致

## 3. 交接动作（30 分钟可完成）

1. 新增维护者写入 `GOVERNANCE.md` §3 维护者名单（自行维护，无中心登记）。
2. 授予仓库权限（至少 triage + merge，不含删除历史）。
3. 在 `docs/review/decisions.md` 记一条 `ADR-00X 维护权交接`。
4. 让新维护者独立完成一次完整流程（合并一个文档 PR + 关闭一个跑题 issue），以验证流程可运转。
5. 创建者退出后不再参与决策，但意见与其他人同权。

## 4. 归档规则

触发条件（任一）：连续 12 个月无实质合并；所有维护者明确退出；仓库被判定不再具备研究价值。

归档步骤：

1. 仓库 README 顶部加 `Status: Unmaintained / Archivable`；
2. 归档 GitHub 仓库（只读）；
3. 在 `CHANGELOG.md` 记一条归档说明与日期；
4. **不得**转让仓库名给任何以本项目名义募资、发行或推广的主体。

## 5. 常见失效模式与处置

| 失效模式 | 表现 | 处置 |
|---|---|---|
| 名义维护 | 只挂名不处理 | 从名单移除，记录理由 |
| 单点依赖 | 只有一人能合并 | 立即增补第二名维护者 |
| 营销化 | README 被改成宣传页 | 回滚，按 ADR-003 处理 |
| 范围漂移 | 开始讨论价格/上币 | 关闭并提示不在范围 |
| 静默放弃 | 长期无响应且不归档 | 任一人可提出归档，按 §4 执行 |

## 6. 不建议做的事

- 不要为本项目申请任何形式的资金（含捐赠、赞助、 grant），会把"无运营主体"变成"有资金主体"。
- 不要建立以项目名义的付费社群。
- 不要以"HEN 团队"自称；正确说法是"贡献者"或"维护者"。
