# 评审流程 / Review Process

**目标**：让每个变更都有可追溯的结论与理由，而不是"谁先合并谁算赢"。

---

## 1. 评审角色

| 评审类型 | 由谁负责 | 创建者角色 |
|---|---|---|
| 草稿期文档审核 | 创建者 + 可选外部读者 | 可参与审改与意见收集 |
| 设计评审（协议变更） | 活跃贡献者形成的评审小组 | 可被咨询，无终审权 |
| 代码评审 | 实现维护者与代码贡献者 | 不审核心代码、不做合并把关 |
| 安全 / 密码学评审 | 独立审计或具备能力的社区安全贡献者 | 不做安全认证 |
| 上线 / 部署评审 | 实施方与社区自行组织 | 不参与、不背书 |

## 2. 流程（按变更类型）

**文档与文字类**（术语、翻译、排版、勘误）：提 PR → 维护者快速处理 → 记入 `CHANGELOG.md`。无需设计评审。

**协议变更**：开 RFC issue（`CONTRIBUTING.md` 模板）→ 至少一名与提案人无关的贡献者复核 → 讨论收敛 → 结论写入 `docs/review/decisions.md`（若形成决策）→ 合并 PR。

**代码实现**：由实现维护者组织代码评审并运行测试；须回填 `docs/handover/test-cases.md` 的通过记录。

**安全相关实现**：必须标注"未审计"；正式落地前应有独立审计评估。未审计而宣称安全，视为违规。

**无活跃评审人时**：变更**不能被认定为通过正式评审**，项目停留在研究阶段。这条不是免责，是规则。

## 3. 评审状态

| 状态 | 含义 | 谁可设置 |
|---|---|---|
| `Draft` | 草稿，打磨中 | 作者/维护者 |
| `Community Review` | 等待社区反馈 | 维护者 |
| `Awaiting Security Review` | 安全审计待完成 | 维护者 |
| `Unmaintained / Archivable` | 无活跃维护者，可归档 | 维护者或任何人提出 |
| `Fork / Independent Implementation` | 独立分叉实现，独立负责 | 分叉方自标 |

状态写在对应文件头部（如 `Status: Draft`），并同步到 `ROADMAP.md` 的进度表。

## 4. 评审判据（顺序不可颠倒）

1. 是否违反白皮书 §2 原则优先级；
2. 是否触碰 §12 合规边界（触及募资、发行、交易服务的提案一律不接收）；
3. 论证是否可被独立复算（引用、仿真、反例）；
4. 是否有回滚路径或兼容方案；
5. 是否至少一名无关贡献者复核过。

## 5. 兜底规则

- 不存在由创建者指派的永久评审团。
- 设计评审依赖活跃贡献者；没有评审人就承认"未评审"。
- 代码与安全评审必须由具备对应能力的人承担。
- 创建者不承担长期评审义务。

## 6. 异议记录

反对意见**不删**。写法：`## 异议 — <日期> <handle>`，写清"反对什么、理由、是否被采纳"。即使最终被否决，也保留在 `docs/review/decisions.md` 或对应 PR 中。

理由：一份只记录"胜利者"的决策史，无法被后来者信任。

## 7. 关闭 issue 的规则

可以关闭：重复、跑题（价格/代币/募资）、无具体主张、要求作者承担开发或法律责任、违反讨论规范。

关闭时必须写一句理由并打标签。不静默关闭。
