## ADR-001 命名与 slug

**状态**：Accepted（2026-11-22）

**背景**：项目需要可检索、可识别、且不被误认为发行资产的名称；中文名此前待定。

**选项**

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. Steady Ledger（原名） | 直译准确 | 通用词组合，检索淹没；像产品名而非项目名 |
| B. Horizon Equilibrium Network（HEN） | 语义对位（长期视野 + 均衡）；缩写可记；不指向资产 | 三词偏长；缩写 `HEN` 在英语中另有语义 |
| C. 中文候选一：衡续网络 | 强调"永续" | 与英文 Horizon 对位弱 |
| D. 中文候选二：衡远网络 | "衡"=均衡、"远"=长期/地平线，与英文对位最紧；二字短 | 需要一句解释才能懂 |

**决定**：英文 `Horizon Equilibrium Network (HEN)`；中文 `衡远网络`；技术副题保留"稳态点对点价值账本"；slug `hen-equilibrium-network`（依 `PROJECT-GUIDE` §2.1）。

**理由**：副题承担解释功能，主名只需可记；中文名与英文语义对位，避免出现"两套不相关的名字"。

**代价（必须知道）**

1. `hen` 在英语中是日常词（母鸡），英文读者可能觉得怪；若在意，可换 `hen-network` 或 `horizon-equilibrium-network`，但这会偏离已定稿 slug，需要一次全局替换。
2. 三字母缩写容易与同名缩写冲突，**发布前须检索 GitHub 组织名与 npm/PyPI 是否占用**。
3. 中文名"衡远"不解释不易懂，所有首次出现处必须附英文名。

**重审触发**：出现商标冲突、或 GitHub 上已被同名占用、或社区一致认为 slug 有歧义。

## ADR-002 沉睡资产：默认不回收

**状态**：Accepted（2026-11-22）；实验分支部分 `Open`

**背景**：初稿的"沉睡资产对冲回流"被读作"协议可没收不活跃资产"。这是公开仓库中最危险的一处表述，既招声誉风险，也涉法律风险。

**选项**

| 选项 | 说明 | 结果 |
|---|---|---|
| A. 保留回收机制并写入基线 | 直接对冲流通萎缩 | 拒绝：等于把"不活跃"当"已放弃"，且极易被实现为没收工具 |
| B. 彻底删除该议题 | 最安全 | 拒绝：流通萎缩是本文主要动因之一，删掉会让 §7 论证失去对手方 |
| C. 默认不回收 + 默认关闭的实验分支（七项条件） | 保住本金不可侵犯，同时保留讨论空间 | **采纳** |
| D. 改为"自愿注销"入口 | 无强制，但对萎缩的作用有限 | 保留为 Q1 候选，未作为基线 |

**决定**：基线写入 P1"本金不可侵犯"；任何回流研究只能作为默认关闭的实验分支，须同时满足七项条件（白皮书 §7.4）。

**理由**：在不牺牲论证完整性的前提下，把最危险的设计移出基线。

**代价**：条款较长；读者可能觉得"说了很多但没做"——这是有意为之，文档只需诚实。

**重审触发**：某辖区法律明确禁止任何形式的资产休眠处理；或 Q1 出现可行的非强制替代机制。

## ADR-003 无代币、无募资、无运营

**状态**：Accepted（2026-11-22）

**背景**：作者为中国公民且不参与开发运营；项目一旦被读作"发币前奏"，风险与误解都会失控。

**决定**：不发行任何资产、不预留份额、不设基金会与金库、不接受捐赠、不提供兑换/中介；对外口径固定为 README 的五条标准回答。

**理由**：移除投机动机后，讨论才会回到机制；同时避免"设计者=发行方"的责任绑定。

**代价**：缺少经济激励，较难吸引长期投入；必须靠文档质量与接手友好度吸引贡献者（这正是 `docs/handover/` 存在的原因）。

**风险应对**：第三方"借壳发币"时，用 README 口径与 `DISCLAIMER.md` 切割，并在 `docs/ecosystem/implementations.md` 移除其链接。

## ADR-004 设计资产与实现资产分离

**状态**：Accepted（2026-11-22）

**背景**：创建者不写核心代码，但仓库又要能被接手。

**决定**：设计资产（白皮书、规范、字段表、取舍、仿真计划、测试用例、风险清单）留在主仓库；实现资产建议另起仓库或以独立目录明确标注归属与状态；主仓库不为任何实现背书。

**理由**：责任边界清楚，避免"文档作者默认对代码负责"。

**代价**：主仓库永远无法"跑起来"，对外容易被误判为"烂尾"。用 README 首段与 `ROADMAP.md` 明确说明。

## ADR-005 状态标签制度化

**状态**：Accepted（2026-11-22）

**背景**：研究型仓库最常见的失败是"看起来什么都做了，其实什么都没验证"。

**决定**：所有产出必须带状态标签（`Draft` / `Community Review` / `Awaiting Security Review` / `Unmaintained` / `Fork`），并在文件头部与 `ROADMAP.md` 同步。

**代价**：维护成本上升；每个文件多一行。

**重审触发**：状态标签开始被滥用为"通过"的同义词时。

## ADR-006 采用 `PROJECT-GUIDE` 的目录结构

**状态**：Accepted（2026-11-22）

**决定**：按 `docs/handover/project-guide.md` §10 重组仓库：`docs/{whitepaper,protocol-draft,research,handover,review,maintenance,ecosystem,legal}` + `spec/` + `examples/sim/` + `contrib/implementations/` + `assets/diagrams/`。

**理由**：审阅者能按"读什么/评什么/接什么/怎么维护"四类路径进入，而不是在一个大文件里翻。

**代价**：文件变多，交叉引用变多，容易出现路径失效——因此 `docs/review/checklist.md` A 部分把"逐条点开链接"列为必检项。

**偏差说明**：`PROJECT-GUIDE` 未列根目录的 `CONTRIBUTING.md` / `GOVERNANCE.md` / `SECURITY.md` / `CODE_OF_CONDUCT.md`。这些是 GitHub 平台惯例且原有内容有效，故保留于根目录，并将操作细节下沉到 `docs/maintenance/`，避免两处各自定义规则。
