# 接手引导 / Onboarding

**给谁看**：想读、想评、想写代码、想接手维护的人。
**前提**：本仓库没有任何可运行代码，也没有网络。你可能是在读一份"还没有实现的设计"。

---

## 0. 先用十分钟判断你要不要继续

回答三个问题：

1. 你能接受"这是一份可能被推翻的草稿"吗？（白皮书 §16，`CHANGELOG.md` 记录了被拒绝的修改）
2. 你能接受"没有团队、没有赏金、没人给你派活"吗？（`GOVERNANCE.md` §2）
3. 你想要的是一份**可讨论的框架**，还是一个**能跑的系统**？如果是后者，本仓库现在给不了。

如果三个都接受，继续。

## 1. 按角色的最短路径

| 你的角色 | 读什么 | 别读 |
|---|---|---|
| 路过看看 | 白皮书 §2、§11、§12 | 全部交接文档 |
| 想挑毛病 | `docs/research/tradeoffs.md` + `docs/research/open-questions.md` | 交接文档 |
| 想写代码 | 本文 → `docs/handover/module-map.md` → `docs/handover/test-cases.md` → `docs/handover/api-sketch.md` | 白皮书 §7 经济细节（可后读） |
| 想接手维护 | 本文 → `docs/maintenance/handover.md` → `docs/maintenance/merge-rules.md` | 白皮书 §6 共识细节 |
| 想引用 | 白皮书 + `CITATION.cff` | 其余 |

## 2. 接手顺序（照做即可）

1. **读问题陈述与目标**（白皮书 §1、§2、§3），确认你理解"本金不可侵犯""权力不可购买"这两条硬约束。
2. **读协议草稿与测试用例**（`docs/protocol-draft/`、`docs/handover/test-cases.md`），注意所有字段都标着"非规范性"。
3. **跑通示例**（`examples/sim/`），只要能跑出结果，就算跨过了"文档到可计算"的门槛。
4. **认领最小模块**，不要一上来写完整节点。建议从"交易解析 + 验签模拟"开始（阶段 2 的第一项）。
5. **按测试用例逐步验证**，每条用例写明你通过了哪条、失败了哪条。
6. **核心共识、密码学、经济模型的变更先开设计评审**，不要在 PR 里顺手改。
7. **稳定后再考虑正式实现与安全评审**；未审计的实现必须自我标注"未审计"。

## 3. 三条不能越的线

- **不发行、不募资、不宣传。** 你写的代码不能包含代币发行、兑换、定价或募资入口（`DISCLAIMER.md`）。
- **不宣称"已上线""已审计""官方"。** 你是贡献者，不是项目方（`GOVERNANCE.md` §7）。
- **不覆盖原作者署名与许可。** MIT 许可与 `CITATION.cff` 须保留。

## 4. 第一个可交付的小任务（建议）

新建 `docs/research/q2_cost_model.md`：给出女巫攻击成本模型的最小版本（攻击者伪造 N 个共识身份的成本 vs 期望收益），并在 `examples/sim/` 里附一个可跑脚本。这份东西会直接决定 P4（能耗上限）能否保留为原则，是当前最有价值的缺口（Q2）。

## 5. 你会遇到的三个挫败点

1. **"字段都在，但没法实现"**——这是正常的，规范还没到可编码的程度（`spec/README.md` 说明原因）。
2. **"每个机制都有反例"**——是的，`docs/research/tradeoffs.md` 就是反例清单。这不是缺陷，是诚实。
3. **"没人回答我的 issue"**——本仓库没有 SLA。没有回应不等于否决，记录会保留（`docs/review/process.md` §5）。
