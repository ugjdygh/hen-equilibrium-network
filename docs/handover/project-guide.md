## 1. 项目定位与创建者边界

### 1.1 项目定位
本项目是一个面向区块链底层账本的开放研究仓库，目标是从零讨论、设计、仿真一套区别于传统比特币范式的去中心化账本原型。当前阶段只沉淀思路、规范草稿、研究问题与可接手的协作框架。

核心研究方向（待定稿）：
- 稳态流通与永续激励；
- 分层对等节点网络；
- 轻量化、低能耗的共识机制；
- 账本可审计与用户隐私可控之间的平衡；
- 自适应参数调节与平滑升级；
- 基础可编程条件交易。

### 1.2 创建者角色边界
仓库创建者只负责：
- 搭建公开仓库骨架；
- 提供初始思路、问题框架与文档草稿；
- 组织前期文档打磨与意见收集；
- 维护初期协作规则与交接说明。

仓库创建者**不负责**：
- 后续核心代码开发；
- 长期代码评审与合并把关；
- 安全审计、密码学实现与生产部署；
- 项目运营、社区管理、上线推进；
- 募资、发币、上交易所、价值承诺；
- 为任何第三方分叉或实现背书。

对外统一口径：
> 本仓库提供研究、设计、规范与仿真类资产；核心实现由后续贡献者独立承接。仓库创建者不交付、不维护、不担保生产代码。

## 3. 白皮书核心思路（草稿，非定稿）

以下内容仅作为后续打磨的问题清单，不构成最终协议规范。

### 3.1 想回应的传统问题
- 固定总量下，私钥丢失、设备损坏、地址沉睡导致资产永久灭失，流通量持续萎缩；
- 区块奖励远期趋近于零，网络安全高度依赖手续费，存在终局激励空洞；
- 纯算力竞争带来高能耗与算力集中；
- 地址与交易全公开，容易被聚类分析与身份溯源；
- 重大参数调整容易引发硬分叉与社区撕裂；
- 原生转账表达能力有限，条件履约、共管、解锁等场景依赖外部系统。

### 3.2 研究中的创新方向
1. **分层对等网络**：普通用户轻节点、验证节点、共识节点分层职责，普通设备可参与，验证层过滤无效交易，共识层负责打包与校验。
2. **轻量混合共识**：保留防女巫、防篡改、无许可参与的基础，同时引入活跃度、验证权重与难度约束，抑制单一算力垄断。
3. **动态稳态经济模型**：不采用固定总量与固定减半，研究沉睡资产对冲回流、低额保底激励、手续费分流与流通量自适应平衡；所有参数必须经仿真验证。
4. **可控隐私遮蔽**：账本可审计、交易可验证，同时降低地址直接关联与画像风险；不承诺绝对匿名。
5. **多维度难度调节**：综合出块间隔、有效算力、节点数量、交易积压与集中度预警指标，设置难度上下限。
6. **基础可编程交易**：支持定时、多重签名、质押锁定、条件履约等有限逻辑；复杂合约留给二层或外部系统。
7. **平滑治理与升级**：预设范围内参数自动微调；超出范围的重大变更走公开提案与讨论；避免强制分叉。

### 3.3 必须保留的研究边界
- 任何经济参数都属于待仿真项，不是发行承诺；
- 隐私方案不等于匿名保护，仍存在去匿名化风险；
- 原型不等于安全实现，未经审计不得宣称可用；
- 所有机制都要写明代价与取舍，不能只写优势。

## 5. 核心代码如何被接手

### 5.1 资产分离原则
仓库内区分两类资产：

| 资产类型 | 内容 | 维护责任 |
|---|---|---|
| 设计资产 | 白皮书、协议规范、字段表、取舍分析、仿真计划、测试用例、风险清单 | 前期由创建者打磨，后续社区共同修订 |
| 实现资产 | 节点代码、钱包、密码学实现、网络程序、生产部署 | 由独立贡献者承接、评审、维护 |

设计资产留在主研究仓库；核心实现建议由贡献者在规范与测试约束下另起仓库，或在主仓中以独立目录明确标注归属与状态。

### 5.2 创建者需要交付的接手材料
- 协议规范文档：字段、编码、签名规则、消息流、出块规则、参数边界；
- 机制说明：设计目标、硬约束、可讨论项、待验证问题；
- 仿真与验证脚本：经济流、难度曲线、沉睡判定、激励流；
- 接口草稿：只定义输入、输出与断言，不写死具体语言实现；
- 测试用例：合法、非法、边界、异常场景；
- 术语表、风险清单、交接说明与贡献流程。

### 5.3 模块交接地图（草稿）

| 模块 | 交接内容 | 验收标准 | 依赖 |
|---|---|---|---|
| 交易结构 | 字段表、编码说明、签名规则 | 可序列化、可验签 | 密码学规范 |
| 区块头 | 版本、哈希、默克尔根、时间戳、难度、随机数 | 可校验完整性 | 交易 / 默克尔 |
| 交易池 | 过滤、排序、积压指标 | 可拒收非法交易 | 交易验证 |
| 轻量验证节点 | 预处理、转发、基础校验 | 通过基础测试用例 | 交易池 |
| 共识节点 | 打包、证明、链选择 | 通过仿真与测试 | 难度 / 网络 |
| 难度调节 | 参数、上下限、权重 | 仿真输出可复现 | 出块统计 |
| 稳态激励 | 保底、回流、手续费分流 | 经济仿真可复现 | 交易池 / 区块 |
| 隐私遮蔽 | 验证证据、关联阻断说明 | 通过边界测试 | 密码学 |
| 升级与治理 | 参数范围、提案流程 | 可区分自动微调与重大变更 | 社区文档 |

每个模块应标注：规范位置、测试位置、仿真位置、开放问题、安全注意事项。

### 5.4 接口示例（非实现）
```text
validate_tx(tx, utxo_set, rules)
  -> (valid, errors, metadata)

validate_block(block, prev_block, difficulty_target)
  -> (valid, reason)

compute_difficulty(history, node_metrics, bounds)
  -> target
```

### 5.5 接手顺序
1. 先读问题陈述与目标，确认理解边界；
2. 读协议草稿与测试用例；
3. 跑通仿真或最小示例；
4. 认领最小模块，不要一上来写完整节点；
5. 按测试用例逐步验证；
6. 核心共识、密码学、经济模型变更先开设计评审；
7. 稳定后再考虑正式实现与安全评审。

## 6. 评审机制

### 6.1 评审角色划分

| 评审类型 | 由谁负责 | 创建者角色 |
|---|---|---|
| 草稿打磨期文档审核 | 创建者 + 可选外部读者 | 可参与审改与意见收集 |
| 设计评审（协议变更） | 后续活跃贡献者形成的评审小组 | 可被咨询，无终审权 |
| 代码评审 | 实现维护者与代码贡献者 | 不审核心代码、不做合并把关 |
| 安全 / 密码学评审 | 独立安全审计或具备能力的社区安全贡献者 | 不做安全认证 |
| 上线 / 部署评审 | 实施方与社区自行组织 | 不参与、不背书 |

### 6.2 评审流程
1. **文档与文字类变更**：术语、翻译、排版、勘误可快速处理；
2. **协议变更**：提交提案，说明影响范围，附仿真、测试或取舍分析，开放讨论；
3. **代码实现**：由实现维护者组织代码评审，运行测试；
4. **安全相关实现**：必须标注“未审计”状态；正式落地前应由独立审计评估；
5. **无活跃评审人时**：变更不能被认定为通过正式评审，项目可停留在研究阶段。

### 6.3 评审状态建议
- `Draft`：草稿，打磨中；
- `Community Review`：等待社区反馈；
- `Awaiting Security Review`：安全审计待完成；
- `Unmaintained / Archivable`：无活跃维护者，可归档；
- `Fork / Independent Implementation`：独立分叉实现，独立负责。

### 6.4 兜底规则
- 不存在由创建者指派的永久评审团；
- 设计评审依赖活跃贡献者；
- 代码与安全评审必须由对应能力的人承担；
- 找不到合适评审人，就不能宣称方案已通过评审；
- 创建者不承担长期评审义务。

## 7. 仓库如何由社区更新

### 7.1 内容分类与更新方式

| 内容 | 更新方式 | 评审与合并 |
|---|---|---|
| README、术语、翻译、排版、勘误 | Fork 后提 PR | 低门槛，维护者快速处理 |
| 协议草稿、白皮书、仿真计划、测试用例 | PR + 讨论 + 变更说明 | 社区 / 维护组评审 |
| 核心实现代码 | 独立目录或另起仓库 | 代码维护者 + 安全评审 |
| 重大设计变更 | 公开提案留痕 | 社区共识，不强行拍板 |

### 7.2 基础更新流程
1. 任何人 fork 仓库并修改；
2. 提交 PR，填写修改说明；
3. 标注影响范围：文档、规范、仿真、实现、安全；
4. 协议类变更关联 Issue 或 Discussion；
5. 开放讨论后由维护者决定合并、修改或关闭；
6. 重要变更同步更新 CHANGELOG 与审核日志。

### 7.3 权限与交接
- **初期**：创建者保留基础合并权，但不包揽所有评审；
- **过渡期**：稳定活跃贡献者可申请维护权限；
- **维护组形成**：由长期活跃贡献者自然确认，不是预设权威；
- **无人维护**：仓库标记待维护或归档，不自动推进；
- **分叉**：分叉版本独立命名、独立维护、独立承担责任。

### 7.4 更新留痕
每次重要更新记录：
- 变更内容与原因；
- 影响模块；
- 对应规范版本；
- 通过的测试或仿真；
- 是否需要复审；
- 是否更新风险清单。

### 7.5 建议标签
- `docs`：文档修订；
- `translation`：翻译；
- `spec`：协议规范；
- `simulation`：仿真调整；
- `security`：安全说明；
- `implementation`：社区实现；
- `archived`：归档 / 暂停。

## 9. 潜在影响与风险

### 9.1 现实影响分层
1. **个人实验原型**：基本没有市场影响，仅限开源学习与机制验证；
2. **社区研究参考**：共识、经济模型、隐私方案、可编程交易思路可能被其他项目参考；
3. **成熟开源网络**：在细分场景形成有限存在感，不会快速替代主流系统；
4. **若被包装为可交易资产**：主要带来投机与监管风险，不构成确定性市场机会。

### 9.2 主要风险
- **安全风险**：个人实现容易存在签名、哈希、重放、双花漏洞；
- **经济风险**：沉睡资产回流、保底奖励、销毁比例失衡可能导致通胀或激励错位；
- **隐私滥用风险**：若被用于非法资金流动，会面临监管打击；
- **合规风险**：不同地区对虚拟资产、隐私币、跨境转账规则不同；国内禁止代币发行融资与交易炒作；
