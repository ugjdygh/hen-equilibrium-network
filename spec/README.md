## 为什么现在是空的

规范（specification）意味着"两个独立实现能据此互通"。要满足这一点，至少需要：编码与序列化、字段的精确语义、错误码全集、消息格式、激活条件、测试向量。

这些目前都不具备，原因有三：

1. **账本模型未定**（Q9，UTXO vs 账户），而它决定所有字段的编码含义；
2. **难度闭环未验证**（Q6），参数边界写进规范就是把未验证的东西固化；
3. **隐私方案未选型**（Q5），而它会改动交易字段与手续费可见性。

把不确定的东西写成规范，比不写更糟：后来者会以为它已验证。

## 什么时候开始写

进入 `ROADMAP.md` 阶段 1 的后期，且满足：

- [ ] Q9 有结论（并已做原型对照）
- [ ] Q6 至少有稳定域扫描结果
- [ ] Q5 至少选定一种候选方案并做过失效分析
- [ ] 区块头与交易字段的编码方案已定
- [ ] 已有一份完整测试向量草案

## 与 `docs/protocol-draft/` 的关系

`docs/protocol-draft/` 是**讨论稿**：字段表、断言、待定项。`spec/` 是**规范**：一旦写入，实现必须遵守，改动需要 RFC 与兼容方案。

**不要把讨论稿的内容复制进 `spec/` 再改写措辞**，那样会产生两份互相矛盾的文件。正确做法是：讨论收敛 → 一次性写规范 → 讨论稿标为 `Superseded`。
